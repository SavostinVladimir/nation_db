# Design

## Context

Мотивация и границы продукта — в `proposal.md`. На 2026-10-27 просмотрены рабочие `main.go` (демонстрационная `main`) и `go.mod` (модуль `database`, директива `go 1.27`); `openspec/config.yaml` выбирает `spec-driven` и не задаёт проектный context. Существующие спецификации отсутствуют по `openspec list --specs`. Это наблюдения рабочего дерева, а не утверждение о готовой функциональности или доступности установленного компилятора.

Подтверждены пользователем: собственный движок на Go, 100 миллионов записей, общий многопользовательский веб-интерфейс и HTTP API. Остальные решения ниже являются предлагаемым дизайном первой версии, а не согласованными пользователем дополнительными требованиями.

## Goals / Non-Goals

**Goals:** единый путь валидации и фиксации для UI/API; дисковые индексы вместо полного сканирования; атомарность записи и двух индексов; ограниченная память при фоновой обработке и восстановлении; воспроизводимая проверка масштаба.

**Non-Goals:** универсальный язык запросов, распределённые транзакции, изменение/удаление записей, поиск по части имени, идентификация реального человека. Не обещается устойчивость к физической потере единственного диска. Веб-ресурсы могут быть HTML/CSS с небольшим браузерным JavaScript; движок, предметная логика и HTTP-сервер пишутся на Go.

## Decisions

### 1. Общий сервис и модель данных

Предлагается один процесс: пакеты движка, контактов и HTTP плюс встроенные веб-ресурсы. Один сервисный слой обслуживает UI и API. Отдельная база для каждого пользователя не создаётся.

Запись хранит `id`, отображаемые `name` и `phone`, а также нормализованные ключи. ID — монотонный беззнаковый 64-битный номер, внешне строка из 20 десятичных цифр с ведущими нулями: строковый и числовой порядок совпадают. При исчерпании диапазона новые записи отклоняются явной ошибкой хранения. Следующее значение восстанавливается из зафиксированного максимума; ID подтверждённых записей не переиспользуются.

Правила нормализации заданы в `specs/contact-records/spec.md`; для имени предлагаются `strings.TrimSpace` и `strings.ToLower`, без языковых эвристик. Телефон приводится к ASCII-цифрам; форматирование сохраняется отдельно. Разрешены несколько строк с одинаковыми нормализованными ключами. Альтернатива «один уникальный телефон на человека» отвергнута: общий номер и несколько телефонов не должны терять связи.

### 2. Единое дисковое пространство ключей

Предлагается собственное хранилище типа LSM: WAL, ограниченные memtable и неизменяемые сортированные дисковые таблицы с фоновым слиянием. Готовые SQLite, PostgreSQL, bbolt, Badger, Pebble и аналогичные движки не используются. Альтернатива — собственное B+ дерево с журналированием страниц; выбрана LSM-организация ради последовательной фиксации добавлений и единого механизма для основных данных и индексов. Это инженерный выбор, не обещание превосходства по скорости.

В одной логической транзакции записываются три ключа: `R|id → запись`, `N|нормализованное имя|id → id`, `P|нормализованный телефон|id → id`. Кодирование границ полей однозначное (длина поля и байты), ID фиксированной длины. Поиск делает диапазонный проход ровно по соответствующему нормализованному ключу и продолжает после ID курсора. Для ответа выполняются точечные чтения `R|id` в том же снимке; отсутствие основной записи при наличии индекса считается повреждением.

Дисковые таблицы имеют версию формата, контрольные суммы блоков и многоуровневый дисковый индекс блоков; в памяти остаётся ограниченный кеш страниц, а не индекс всех ключей. Слияния потоковые. Размер memtable, кеша, числа одновременно сбрасываемых таблиц и буферов слияния ограничен конфигурацией. При отставании сброса применяется обратное давление на запись; новые таблицы в памяти не накапливаются бесконечно.

### 3. Протокол записи и согласованность

Один сериализованный писатель назначает ID и порядковый номер фиксации. WAL хранит версионированные кадры с длиной, данными целой операции и контрольной суммой. После полного добавления кадра выполняется синхронизация WAL; только затем операция публикуется в memtable вместе с двумя индексами под общей границей фиксации и возвращается `201`. Групповая синхронизация допустима, если каждый ответ ждёт синхронизации своей группы.

Читатель фиксирует номер видимой операции и ссылки на неизменяемые дисковые поколения и memtable. Один ответ не смешивает части разных публикаций. Ссылки удерживают необходимые файлы до завершения чтения. Между HTTP-страницами снимок не удерживается: курсор содержит версию, тип поиска, нормализованный ключ и последний ID; его длина и структура проверяются. Курсор не является средством авторизации.

При ошибке WAL или синхронизации писатель переходит в состояние ошибки и прекращает новые создания до восстановления; чтения уже опубликованных данных остаются доступны, пока не обнаружена ошибка чтения. Неизвестный исход операции не маскируется гарантией exactly-once: клиенту предлагается поиск перед повтором. Альтернатива с обязательным idempotency key отложена как отдельная возможность.

### 4. Сброс, восстановление и слияния

Полная memtable вместе со всеми тремя видами ключей сбрасывается в новую таблицу. Таблица записывается во временный файл, синхронизируется и проверяется; затем атомарно публикуется новое поколение manifest с перечнем файлов и границей WAL, покрытой сбросом. Manifest и каталог синхронизируются. WAL-сегменты удаляются только после устойчивой публикации покрывающего их manifest. Слияния используют тот же порядок; старые файлы удаляются после публикации и освобождения читателей. Авария оставляет доступным старое либо новое полное поколение; промежуточные файлы без ссылки не принимаются за действующие.

При старте процесс эксклюзивно блокирует каталог, проверяет версию manifest и восстанавливает операции WAL после зафиксированной границы. Потоковое воспроизведение использует те же лимиты памяти и промежуточные сбросы, что обычная загрузка. Оборванный кадр в конце последнего WAL-сегмента может быть отброшен; полные кадры с неверной контрольной суммой, повреждение внутри журнала и повреждение действующих таблиц являются явной ошибкой. Неподдерживаемая версия не открывается на запись. Автоматическая «починка» с пропуском повреждённых данных запрещена.

Минимальная платформа гарантий первой версии — Linux и локальная файловая система с корректной поддержкой синхронизации файлов, каталогов и атомарного переименования. Проверки с принудительным завершением процесса и внедрением ошибок необходимы; потеря питания моделируется файловым тестовым слоем. Поддержка других платформ не заявляется до отдельной проверки этих операций.

### 5. API и визуальная оболочка

Контракт маршрутов, кодов и пагинации — `specs/contact-http-api/spec.md`. UI выполняет запросы к тому же origin, выводит пользовательские поля текстом, блокирует повторную отправку активной формы и отбрасывает запоздавшие результаты старого поиска. Сценарии пользователя — `specs/contact-web-ui/spec.md`. Отдельный публичный API пакетной загрузки для первой версии не требуется.

Предлагаемый режим — доверенная сеть с ограничением доступа на уровне среды; все подключённые пользователи имеют одинаковые права чтения и добавления. Сервер по умолчанию слушает loopback, адрес для общей сети задаётся явно. Интернет-публикация потребует отдельного change с аутентификацией и защитой транспорта; текущий дизайн её не предусматривает.

### 6. Проверочный профиль и критерии приёмки

Обязательный масштаб проверки — подтверждённые пользователем 100 миллионов записей. Linux/8 CPU/16 GiB/SSD 500 GiB — пример начальной конфигурации стенда, не условие приёмки и не гарантия достаточности. Аппаратные ресурсы и расход памяти/диска документируются по фактическому прогону; обязательный порог RSS не устанавливается. Показатели времени не выдумываются: измеряются длительность загрузки/восстановления и p50/p95/p99 поиска, а SLA скорости не устанавливается без результатов. Дисковая организация и ограниченные буферы остаются архитектурными решениями.

Воспроизводимый Go-генератор с seed создаёт 100 000 000 записей через тот же сервисный путь валидации и долговечной фиксации. Обход журнала, отключение синхронизации и подмена дискового движка не допускаются. Пример распределения: 1 000 000 записей с одним популярным именем, 100 000 других записей с одним общим телефоном, 10 000 точных повторов одной пары, остальные — детерминированные пары с кириллицей/латиницей и телефонами длиной 11–15 цифр. Пример длины имён — 8–64 кодовых точки, в том числе варианты регистра; ввод телефонов включает разрешённые разделители. Конкретные доли и длины можно менять: обязательны полный объём, фиксированные seed/параметры, покрытие обоих направлений, повторов и больших групп совпадений. Группы генерируются раздельно; ожидаемые ответы выводятся из seed и номера записи без хранения второй полной базы в памяти. Имена/телефоны у границ валидации проверяются отдельными функциональными тестами; результаты относятся к задокументированному распределению.

Приёмка включает: загрузку полного объёма с работающими слияниями; 10 конкурентных клиентов (создания и оба поиска); сравнение не менее 10 000 детерминированных запросов с эталоном; полный проход страниц популярных групп; перезапуск и повтор выборки; контроль RSS и максимального расхода диска в каждой фазе. Дополнительные записи конкурентной фазы учитываются отдельно. Для проверки пагинации неизменного набора запись приостанавливается. Для измерения запросов фиксируются размер страницы 50, пропорция направлений 50/50, наличие/отсутствие совпадений, состояние кеша, число клиентов и длительность фазы (не менее 10 минут). Отчёт полного прогона обязателен; короткий CI-прогон не заменяет проверку 100 миллионов.

Надёжность отдельно проверяется на небольшом эталонном наборе: остановки до/после синхронизации WAL, во время публикации manifest, сброса и слияния; ошибки записи, отсутствие места, оборванный хвост и повреждённые контрольные суммы. После восстановления ни один подтверждённый ID не исчезает, каждая видимая запись обнаруживается обоими индексами. Это проверка будущей реализации, сейчас измерения не проводились.

## Risks / Trade-offs

- [Сложность собственного движка] → отделить протокол фиксации и дисковый формат, проверять аварийные границы до подключения UI.
- [Рост диска во время слияний] → ограничивать параллельные слияния, оставлять резерв и проверять максимальное, а не только итоговое потребление.
- [Горячие имена/телефоны] → составные индексные ключи и потоковая пагинация без сборки всех совпадений.
- [Повтор POST после потери ответа] → явный неизвестный исход, поиск и предупреждение о возможном дубликате.
- [Неизвестные требования к ресурсам] → полный прогон и документирование фактических ресурсов; при нехватке памяти/диска настройка буферов и стенда либо пересмотр архитектуры до заявления готовности.
- [Единственный носитель] → описать остановку сервера и копирование полного каталога для внешнего резервирования; это эксплуатационная процедура, не онлайн-сервис резервных копий.

## Migration Plan

Миграции существующих пользовательских данных нет: их формат и реализация в просмотренных источниках отсутствуют. Первый запуск создаёт версионированный каталог; повторный открывает его без очистки. Инструкция запуска описывает адрес, каталог, остановку, повторный запуск и восстановление офлайн-копии в отдельный каталог. Обновление несовместимого формата не выполняется молча. Откат выполняется совместимым бинарным файлом либо полной сохранённой копией каталога после остановки; экспериментальные данные не перезаписываются автоматически.
