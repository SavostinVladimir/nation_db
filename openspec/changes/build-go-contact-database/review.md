## Основание и версия

Исходный запрос: создать спецификацию через OpenSpec для «хорошей» базы данных с визуальным интерфейсом и программным API, хранением имён и телефонов, поиском имён по телефону и телефонов по имени, надёжным хранением многих записей и реализацией с нуля на Go.

Идентификаторы исходных требований:

- U-01 — «Должна быть хорошей базой данных».
- U-02 — «Должна иметь Визуальный Пользовательский Интерфейс и программное API».
- U-03 — «Должна хранить Имена и Телефоны».
- U-04 — «Можно искать Имена по номеру Телефона».
- U-05 — «Можно искать Телефоны по Имени».
- U-06 — «Должна надежно хранить много записей».
- U-07 — «Написана с нуля на golang».

Явные уточнения пользователя:

- U-08 — «Собственный движок хранения на Go».
- U-09 — «100 миллионов записей».
- U-10 — «Веб-интерфейс и HTTP API, общий доступ нескольких пользователей».

Иные решения — предложения проекта, не дополнительное пользовательское одобрение. Реализация не входила в задачу и не выполнялась.

Проверены `proposal.md`, `design.md`, `tasks.md` и четыре `specs/*/spec.md`. Проведены два раунда на фиксированных копиях: `r1-3b33f30c21c76e59` и итоговый **`r2-5afa4f4a86284219`**. Документы не закоммичены; версия фиксируется SHA-256 в [review-revision.json](review-revision.json), а не ссылкой на коммит. Все пять ролей проверили финальную версию. Каждый первоначальный запуск имел `fork_turns="none"`; ревьюеры получали одинаковый пакет с оригинальным запросом и источниками, без истории автора и мнений других ревьюеров. Во втором раунде часть ролей повторно проверяла новый snapshot в своих независимых контекстах.

## Замечания второго раунда и решение автора

### EX-1 — major по оценке spec-excess

**Расположение:** design, §6; tasks 7.1–7.3. Ревьюер предлагает сделать необязательными точные параметры методики: seed, число клиентов и эталонных запросов, длительность измерений, обход больших групп, отчёт и аварийные остановки. Основание: пользователь назвал масштаб и надёжность, но не задавал отдельный бенчмарк.

**Решение:** не принято как дефект границ продукта. Проверка полного объёма и восстановление после сбоев необходимы для U-06/U-09; без воспроизводимого набора, эталона, обхода результатов и аварийных проверок эти требования нельзя убедительно принять. Числа в методике являются предлагаемым планом проверки, а не ограничением числа пользователей или SLA продукта. Обязательная задача не добавляет публичный сервис, дополнительную платформу или требование покупки определённого оборудования. Аппаратные пороги уже сняты; скорость только измеряется. Автор сохраняет конкретную методику для исполнителя. Расхождение с оценкой spec-excess зафиксировано, единогласного одобрения нет.

### EX-2 — minor по оценке spec-excess

**Расположение:** tasks 3.5; design, Risks / Trade-offs и Migration Plan. Ревьюер предлагает убрать обязательную документацию и проверку офлайн-копирования/восстановления как дополнительную эксплуатационную работу.

**Решение:** оставлено как минимальная процедура сохранения собственных данных, связанная с U-06. Это остановка процесса, копирование полного каталога и проверка открытия копии, а не реализация отдельной системы резервирования. Процедура также нужна для безопасной работы с новым собственным дисковым форматом. Отказ от гарантии пережить физическую потерю диска не исключает инструкции по внешней копии.

## Готовность и ограничения

Спецификация готова к рассмотрению и реализации в описанных границах с зафиксированным выше расхождением о детализации приёмочной методики. Неразрешённых продуктовых вопросов, требующих нового решения пользователя для подготовки этих артефактов, не выявлено. Успешно выполнено `openspec validate build-go-contact-database --strict`.

Предлагается один сервер в доверенной сети без разграничения прав: общая база означает одинаковые права чтения и добавления у подключённых пользователей. Применимость к публичному интернет-сервису этим change не заявляется. Объём 100 миллионов — критерий будущей проверки, не уже достигнутый результат. Задачи реализации остаются неотмеченными.
