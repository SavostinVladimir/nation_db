# Spec Delta

## Purpose

Предоставить программам и веб-интерфейсу единый HTTP JSON контракт создания записей и поиска имён и телефонов в общей базе.

## ADDED Requirements

### Requirement: Создание через HTTP
API SHALL принимать `POST /api/v1/records` с JSON-объектом ровно из строковых полей `name` и `phone`, применять правила contact-records и возвращать `201` с объектом `{id,name,phone}` только после устойчивого сохранения. Тело запроса SHALL ограничиваться 8 KiB. Неверный JSON, типы и неизвестные поля SHALL отклоняться.

#### Scenario: Успешный POST
- **WHEN** клиент отправляет `{"name":"Анна","phone":"+7 999 123-45-67"}` с `Content-Type: application/json`
- **THEN** получает `201`, `Content-Type: application/json` и сохранённую запись с новым строковым ID
- **AND** последующий поиск по каждому полю возвращает эту запись

### Requirement: Поиск через HTTP
API SHALL принимать `GET /api/v1/records?name=...` либо `GET /api/v1/records?phone=...`, ровно один поисковый параметр. Успешный ответ SHALL быть `200` с `{items:[{id,name,phone}],next_cursor:string|null}`; отсутствие совпадений — `items:[]` и `next_cursor:null`. Неизвестные и повторяющиеся параметры SHALL отклоняться.

#### Scenario: Программный поиск
- **WHEN** разработчик выполняет GET с URL-кодированным полным именем
- **THEN** получает JSON-список связанных телефонов в виде записей и может прочитать исходное отображаемое имя каждой из них

#### Scenario: Неоднозначный запрос
- **WHEN** запрос содержит одновременно `name` и `phone` либо не содержит ни одного
- **THEN** API возвращает `400` с кодом `invalid_query`

### Requirement: Пагинация результатов
API SHALL поддерживать `limit` (целое 1–100, по умолчанию 50) и непрозрачный `cursor`. Результаты SHALL идти по возрастанию ID. Курсор SHALL быть привязан к нормализованному запросу и задавать продолжение после последнего ID. Между страницами нет общего снимка: новые записи с большими ID могут появиться на следующих страницах; ранее выданные ID не повторяются.

#### Scenario: Продолжение выборки
- **WHEN** в неизменной базе есть 120 совпадений и клиент следует курсорам с `limit=50` до `null`
- **THEN** получает страницы 50, 50 и 20 и все 120 записей ровно один раз

#### Scenario: Неверный курсор
- **WHEN** курсор повреждён, не поддерживается или передан с другим нормализованным поисковым ключом
- **THEN** API отвечает `400` с кодом `invalid_cursor`, не начиная поиск с первой страницы молча

### Requirement: Ошибки API
API SHALL возвращать JSON `{error:{code,message,field?}}`: `400` для `invalid_json`, `invalid_query`, `validation_error`, `invalid_cursor`; `413` для `payload_too_large`; `415` для `unsupported_media_type`; `503` для `storage_unavailable`; `500` для `internal_error`. Сообщение SHALL быть понятным без стека вызовов и внутренних путей. Неуспешный ответ SHALL не подтверждать сохранение.

#### Scenario: Ошибка поля и ошибка хранения
- **WHEN** клиент передаёт пустое имя
- **THEN** получает `400`, `validation_error`, `field:"name"` и причину
- **AND** при невозможности устойчивой записи валидных данных получает `503` и `storage_unavailable` без объекта успешно созданной записи

### Requirement: Путь разработчика от записи до результата
Документация API SHALL содержать воспроизводимый путь: адрес запущенного сервера, POST записи, чтение ID из ответа, оба GET-поиска, обход страниц и разбор ошибки. Риск дубликата при повторе запроса с неизвестным исходом SHALL быть указан явно.

#### Scenario: CUJ разработчика
- **GIVEN** разработчик имеет адрес доступного сервера и пример запросов
- **WHEN** отправляет POST с именем и телефоном, видит `201` и ID, затем выполняет GET по телефону и GET по имени
- **THEN** в обоих JSON-ответах узнаёт свою запись по тому же ID; цель программной записи и двустороннего поиска достигнута
- **AND** при ошибке валидации видит поле и причину, исправляет ввод и повторяет запрос; при обрыве ответа сверяет поиск перед осознанным повтором, который может создать дубликат
