# Spec Delta

## Purpose

Позволяет найти все имена, связанные с телефоном, и все телефоны, связанные с именем, с предсказуемыми правилами совпадения и выдачи больших результатов.

## ADDED Requirements

### Requirement: Lookup by phone
Система SHALL искать контакты по полному ключу телефона с теми же правилами проверки и нормализации, что при добавлении. Результат SHALL содержать все совпадающие контакты с `id`, `name`, `phone`, включая разные имена для одного номера.

#### Scenario: Find names using a formatted number
- **GIVEN** сохранены `Анна / +7 (999) 123-45-67` и `Борис / 79991234567`
- **WHEN** пользователь ищет `+7 999 123 45 67`
- **THEN** результат содержит оба контакта с исходными формами их телефонов

### Requirement: Lookup by name
Система SHALL искать по полному имени после той же проверки и удаления внешних пробелов, что при добавлении. Сравнение SHALL быть точным и учитывать регистр, внутренние пробелы и последовательность Unicode-кодовых точек. Результат SHALL содержать все совпадающие контакты с `id`, `name`, `phone`.

#### Scenario: Find multiple phones by an exact name
- **GIVEN** у имени `Анна` сохранены два разных телефона и существует отдельный контакт `анна`
- **WHEN** пользователь ищет ` Анна `
- **THEN** результат содержит два контакта `Анна` и не содержит `анна`

#### Scenario: No substring matching
- **GIVEN** сохранён контакт с именем `Анна Петрова`
- **WHEN** пользователь ищет `Анна`
- **THEN** этот контакт не входит в результат

### Requirement: Empty and invalid lookup results
Система SHALL возвращать пустой успешный результат для корректного запроса без совпадений. Пустой или некорректный поисковый ввод SHALL возвращать ошибку валидации, а не список всех записей. Ошибка чтения хранилища SHALL отличаться от отсутствия совпадений.

#### Scenario: No matches
- **WHEN** выполнен корректный поиск номера, отсутствующего в базе
- **THEN** результат содержит пустой список и признак отсутствия следующей страницы

#### Scenario: Invalid query
- **WHEN** пользователь ищет имя из одних пробелов или телефон `abc`
- **THEN** система сообщает ошибку соответствующего поля и не выполняет поиск всех контактов

#### Scenario: Storage read fails
- **WHEN** при поиске невозможно прочитать соответствующую запись с диска
- **THEN** система сообщает ошибку хранилища и не выдаёт её за пустой успешный результат

### Requirement: Deterministic bounded pagination
Система SHALL выдавать совпадения по возрастанию числового `id`, по 50 записей по умолчанию, с `limit` от 1 до 100 и необязательным `after_id`. Следующая страница SHALL содержать только совпадения с `id > after_id`. Ответ SHALL включать `next_after_id` последней выданной записи при наличии продолжения и `null` иначе.

#### Scenario: Read all pages without omissions
- **GIVEN** для одного имени существуют 125 контактов
- **WHEN** клиент последовательно запрашивает страницы с `limit=50`, используя возвращённый `next_after_id`
- **THEN** страницы содержат 50, 50 и 25 контактов, все 125 возвращены по одному разу
- **AND** последняя страница содержит `next_after_id: null`

#### Scenario: Insert between pages
- **GIVEN** первая страница уже прочитана
- **WHEN** добавлен новый совпадающий контакт и клиент запрашивает следующую страницу
- **THEN** уже выданные контакты не повторяются, а новая запись может появиться на последующих страницах согласно её `id`
- **AND** система не обещает снимок данных на момент первой страницы

#### Scenario: Invalid or unrelated cursor
- **WHEN** клиент передаёт `limit=0`, `limit=101`, отрицательный, нулевой или нечисловой `after_id`
- **THEN** система сообщает ошибку валидации
- **WHEN** положительный `after_id` отсутствует в базе или относится к другому имени
- **THEN** он используется только как числовая нижняя граница для текущего поиска

### Requirement: Visibility after a successful add
После подтверждения добавления система SHALL делать контакт доступным обоим направлениям поиска и чтению по `id`. Конкурентные чтения SHALL возвращать только полные контакты и не наблюдать частично добавленную запись.

#### Scenario: Search immediately after adding
- **WHEN** клиент получил успешный ответ на добавление контакта и сразу ищет его по имени и телефону
- **THEN** оба запроса находят подтверждённый контакт
