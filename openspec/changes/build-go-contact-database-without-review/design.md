# Design

## Context

Мотивация и границы первой версии описаны в `proposal.md`, поведение — в пяти `specs/*/spec.md` этого изменения. В рабочем каталоге нет исходного кода приложения: предстоит создать Go-модуль и компоненты. Конфигурация OpenSpec использует `spec-driven` и не задаёт дополнительных ограничений. Существующие спеки и другие изменения не использовались; `spec-review` и его субагенты исключены по прямому указанию пользователя.

Неопределённые вводные конкретизированы как допущения предложения: одна локальная база, точное совпадение имени, до миллиона контактов в контрольном профиле, добавление и чтение без изменения и удаления. Численные цели являются критериями будущей реализации, а не результатами уже проведённых измерений.

## Goals / Non-Goals

**Goals:**

- Обеспечить один путь валидации и добавления для API и UI.
- Иметь единственный источник постоянных данных, восстанавливаемые индексы и определённую границу подтверждения записи.
- Уложиться в заданный профиль за счёт индексного поиска и чтения с диска только выдаваемых контактов.
- Собрать сервер, UI и служебные команды в один исполняемый файл.

**Non-Goals:**

- Не проектировать универсальный движок SQL, произвольные транзакции, дисковые индексы или онлайн-компактацию в первой версии.
- Не гарантировать неограниченный рост: индексы зависят от числа контактов, а подтверждённый профиль ограничен миллионной базой.
- Первая реализация рассчитана на Linux и macOS с локальной файловой системой, поддерживающей синхронизацию и процессные блокировки. Windows и сетевые файловые системы требуют отдельного решения и не входят в проверяемый профиль.

## Decisions

### 1. Модули и единая прикладная логика

Планируемая структура:

| Область | Ответственность |
| --- | --- |
| `cmd/contactdb` | команды `serve`, `backup`, `restore`, параметры запуска и коды завершения |
| `internal/contacts` | поля контакта, проверка и нормализация, добавление и поиск |
| `internal/storage` | формат файла, блокировка, журнал, индексы, восстановление и копирование |
| `internal/httpapi` | маршруты `/api/v1`, JSON, параметры и преобразование ошибок |
| `internal/web` | встроенные HTML/CSS/JavaScript и их раздача |

Использовать стандартную библиотеку Go. UI — обычные HTML, CSS и JavaScript, встроенные через `embed`. HTTP — `net/http`, CRC — `hash/crc32`, операции с файлами — `os`. Это исключает внешний сервер ресурсов и готовый движок СУБД. Альтернатива SQLite уменьшила бы риск работы с файлами, но не соответствует принятому толкованию «база написана с нуля». Отдельный JavaScript-фреймворк не нужен для двух форм и списка результатов.

`serve --data <directory> --port 8080` слушает `127.0.0.1`; адрес после открытия базы выводится в журнал запуска. Сначала полностью открыть и восстановить хранилище, затем принимать HTTP-запросы. Параметр `--data` обязателен: отсутствие данных в ошибочно выбранном каталоге не должно молча скрываться за другой базой. Новый отсутствующий или пустой каталог можно инициализировать. Если существующий непустой каталог не содержит ожидаемую базу, отказать с диагностикой; не создавать поверх него пустую.

### 2. Один журнал является постоянной базой

Каталог содержит `contacts.log` и служебный файл блокировки `.lock`. Файл журнала начинается с фиксированного заголовка: 8 байт magic, uint32 версии и CRC32C заголовка. Версия первой реализации — 1. Все числовые поля двоичного формата — little-endian.

Каждая запись: uint32 длины payload, payload и uint32 CRC32C длины вместе с payload. Payload содержит uint64 `id`, uint16 длины имени, uint16 длины исходного телефона и соответствующие UTF-8-байты. Максимум payload — 4 KiB; длины проверяются до выделения памяти. Ключ телефона не хранится отдельно и вычисляется при чтении. Индексы не являются частью постоянного формата.

Последовательный журнал проще согласовывать, чем отдельные таблицы и постоянные индексы. Он одновременно хранит данные и обеспечивает восстановление; отдельный WAL не нужен, поскольку нет обновлений на месте. Формат документируется и покрывается совместимыми тестовыми образцами. Версия не меняется без явного изменения формата.

### 3. Добавление имеет одну точку фиксации

После общей валидации сериализовать добавления одним mutex. Под блокировкой проверить здоровье хранилища и уникальность пары, назначить следующий uint64 `id`, закодировать полную запись, дописать её и выполнить `File.Sync`. Только затем опубликовать контакт во всех индексах и вернуть прикладной успех, который API преобразует в `201`.

При создании новой базы синхронизировать заголовок файла и запись его имени в каталоге до приёма добавлений; при создании самого каталога синхронизировать соответствующий родительский каталог. Это необходимо для первого успешного добавления, а не только последующих.

Ошибка записи, короткая запись или ошибка синхронизации переводит хранилище в неисправное состояние. Не продолжать добавления в потенциально неполный хвост, не выдавать успешные ответы и не пытаться автоматически повторять запись. Последующие операции с данными возвращают `503` до перезапуска. Ошибка чтения записи также делает хранилище неисправным. Запрос, пересекающийся с моментом отказа, может завершиться чтением уже проверенных данных; новые операции после фиксации отказа не обслуживаются.

Сбой после синхронизации, но до ответа клиенту может оставить полный контакт. Это допустимая неопределённость: повтор добавления получает `409` с существующим `id`. После штатной остановки сервер перестаёт принимать новые запросы, завершает уже выполняющиеся записи и закрывает файлы. При аварийной остановке гарантия опирается на `Sync`, а не на обработчик завершения.

Альтернатива — пакетное подтверждение нескольких записей — может увеличить скорость, но усложняет первый вариант; начать с синхронизации каждой записи. Асинхронное сохранение после `201` неприемлемо.

### 4. Индексы в памяти и дисковое чтение результатов

Хранить отображения `name -> []id`, `phoneKey -> []id`, `(name, phoneKey) -> id` и таблицу `id -> (offset, length)`. Идентификаторы начинаются с 1 и возрастают при каждом успешном добавлении. При восстановлении продолжать с максимального сохранённого значения; подтверждённый `id` никогда не переиспользуется. В JSON передавать `id` строкой, чтобы браузер не терял точность uint64.

Списки `id` естественно упорядочены порядком добавления. По `after_id` бинарным поиском найти начало и получить не более `limit + 1` совпадений; дополнительное совпадение определяет наличие продолжения. Для ответа прочитать с диска только `limit` записей через `ReadAt`, проверить их структуру и CRC. Полный текст всех контактов не дублировать в отдельном кэше.

RWMutex защищает публикацию индексов; читатель копирует ограниченный набор позиций под read-lock, затем освобождает его до дискового чтения. Публикация всех индексов одного контакта атомарна относительно читателей. Выдача страниц не является историческим снимком, что явно отражено в контракте.

Альтернатива с постоянным B-tree снизила бы потребление RAM на очень больших базах, но потребовала бы дополнительного протокола согласования и восстановления. Индексы в памяти достаточны для принятого профиля; это проверяется измерениями, а не предполагается доказанным заранее.

### 5. Открытие, восстановление и исключительное владение

До любых операций получать неблокирующую процессную блокировку `.lock`. На Linux/macOS использовать адаптер системной файловой блокировки, удерживаемой открытым дескриптором. Наличие файла само по себе не означает занятую базу. Сервер и обе служебные команды используют один протокол. После падения процесса ОС освобождает блокировку; удалять `.lock` для разблокировки нельзя.

Открытие проверяет заголовок и последовательно читает весь журнал. Проверять длины, CRC, возрастающие последовательные `id`, валидность полей и уникальность пар; строить временные индексы. EOF на границе записи — нормальное завершение. Оставшиеся менее четырёх байт длины либо недостаток байт для payload/CRC при допустимой длине — неполный хвост. Полная запись с неверным CRC, недопустимая длина, нарушение структуры или неизвестный заголовок — ошибка, а не повод пропустить запись.

Не изменять файл, пока весь доступный префикс не проверен. Только при единственном неполном хвосте обрезать его до последней полной записи, синхронизировать файл и вывести диагностическое сообщение с позицией. Ошибка при этой операции также блокирует запуск. При любой другой ошибке оставить исходный файл без изменений и завершить запуск. Повреждённый заголовок, даже в пустой базе, не заменять новым автоматически.

Этот протокол различает штатный обрыв последней записи и обнаруженное повреждение, но не обещает исправить произвольную порчу диска. Полный повреждённый финальный кадр требует восстановления из копии.

### 6. Резервное копирование и восстановление

Команды: `backup --data <source> --out <backup-directory>` и `restore --from <backup-directory> --data <target>`. Исходный и целевой каталоги не должны совпадать или быть вложены друг в друга; символические ссылки на эти каталоги не принимаются. Оба каталога блокируются на время операции в стабильном порядке по абсолютному пути. Требование отсутствующего или пустого назначения проверяется до создания в нём служебных файлов.

Для копирования применять строгое чтение: неполный хвост копии или источника — ошибка, исходник не исправлять. После аварии оператор сначала запускает сервер для обычного восстановления, останавливает его и затем создаёт копию. Перед копированием проверять весь источник, писать во временный файл назначения, проверять результат, выполнять синхронизацию, переименовывать его в `contacts.log` и синхронизировать каталог назначения. `.lock` не копировать. Полный успех выводить только после завершения всех стадий.

Восстановление использует тот же проверяющий и копирующий код. При ошибке удалить только временные файлы, созданные текущей командой; не затрагивать исходник и чужие файлы. Команда не заменяет непустой каталог и не открывает базу одновременно с сервером. Горячая копия потребовала бы снимков или координации с writer и отложена.

### 7. HTTP и браузер

Маршруты и статусы заданы в `contact-http-api`. Статические маршруты поиска должны различаться с маршрутом чтения по идентификатору. Для POST сначала ограничить чтение тела 4 KiB и проверить UTF-8, затем разобрать ровно один объект с учётом повторных ключей; одного `encoding/json` с поведением по умолчанию для этого недостаточно. Поля и поисковые значения пропускать через общую прикладную проверку. Запрещённые управляющие символы имени проверяются в исходном вводе до удаления внешних пробелов. Телефон хранится с удалёнными внешними ASCII-пробелами, а поиск использует только цифры.

Ошибки прикладного слоя типизированы: валидация, дубликат, отсутствие, недоступное хранилище; HTTP-слой назначает им заданные коды. Внутренние пути и детали ошибок файлов не включать в клиентский текст; в серверной диагностике указывать причину без полного содержимого контактов. Для HTTP задаются конечные таймауты чтения и записи. CORS для других origin не включать; браузер использует относительные URL.

UI отправляет запросы через `fetch`, формирует query через `URLSearchParams`, выводит данные через `textContent`. Две формы имеют подписанные поля, кнопки и области статуса. Сохранение блокируется до завершения запроса. Поиск использует номер поколения запроса и отмену предыдущего запроса; старый ответ не может заменить новый. Пагинация привязана к поколению поиска, кнопка загрузки страницы блокируется до ответа. Повтор после ошибки страницы сохраняет уже загруженные результаты и тот же курсор.

### 8. Доказательства готовности

- Модульные проверки: границы имени и телефона, точные ключи, эквивалентное форматирование, уникальность пары, значения `id` вне безопасного диапазона чисел JavaScript, пагинация.
- Тесты хранения: штатное открытие, принудительное завершение процесса, обрывы записи на границах кадра, ошибки записи и синхронизации, повреждение CRC, неизвестная версия, блокировка между процессами, копия и восстановление без перезаписи назначения.
- HTTP-проверки через `httptest`: полные циклы, форматы, методы, граничные тела, повторные ключи, Unicode, поля ошибок и недоступное хранилище.
- Проверка конкуренции под `go test -race`: одновременное добавление одинаковой пары, чтение во время записи, согласованная публикация индексов.
- Браузерная проверка CUJ из `contact-web-ui`: первое открытие, сохранение, оба поиска, несколько страниц, ошибки, запоздалый ответ, текст с разметкой, клавиатура и окно 360 px.
- Отдельный воспроизводимый нагрузочный запуск по профилю `durable-contact-storage`, с зафиксированными seed, конфигурацией машины и версией сборки. Генерация миллиона записей находится вне времени измерений; тестовый генератор не становится пользовательским импортом. Проверять RSS во время открытия, поиска и добавления. В протокол включить p95, число ошибок и проверку данных после повторного запуска.

Kill-тест доказывает устойчивость к завершению процесса. Ошибки `Sync` и тесты границ записи проверяют протокол; они не являются физическим испытанием отключения питания. Гарантия при отключении питания ограничена указанным в требованиях поведением носителя.

## Risks / Trade-offs

- Самостоятельный файловый движок увеличивает риск ошибок сохранности → минимальный формат, один writer, синхронизация до ответа, fault injection и восстановление из проверенной копии.
- Индексы растут с объёмом базы → измерять пиковую RSS на контрольном наборе; рост за пределами миллиона требует отдельного профиля и, возможно, дисковых индексов.
- Восстановление линейно по объёму журнала → принять сканирование для первой версии и проверить предел запуска 60 секунд; не вводить ненадёжные кэши ради времени старта.
- `Sync` каждой записи ограничивает скорость → проверять заданный p95; оптимизацию пакетов рассматривать только с сохранением границы подтверждения.
- Неизвестный исход запроса после сетевого обрыва → уникальность пары, возврат существующего `id` и соответствующее сообщение UI.
- Контрольные суммы обнаруживают повреждения, но не восстанавливают их → остановка без изменения источника и отдельная резервная копия; копия на том же носителе не защищает от отказа всего носителя.
- Точное имя чувствительно к регистру и Unicode-представлению → явно объяснить правило в UI и API-документации; нечёткий поиск потребует отдельного изменения.

## Migration Plan

Существующих прикладных данных и формата для миграции в рамках этого изменения нет. Первая поставка включает бинарный файл, встроенный UI и документацию: сборка, запуск с новым каталогом, добавление и поиск, остановка, копирование и восстановление.

Перед заменой бинарного файла оператор останавливает сервер и создаёт резервную копию. Откат на версию, понимающую формат 1, выполняется заменой бинарного файла с сохранением каталога; неподдерживаемый формат должен завершать запуск, а не преобразовываться автоматически. Для отката данных используют проверенную копию в другом пустом каталоге; новые данные после создания копии в неё не входят.
